# payOS post-trip payment

User approved the recommended hosted-checkout integration in chat on 2026-11-24. The user subsequently removed the proposed prepayment feature. Implement post-trip payOS only; retain the existing simulated provider for legacy tests and API clients.

## Behavior
- The booking UI creates trips with `paymentProvider: PAYOS`. Omitted provider defaults to `MOCK` for existing clients; validation accepts only these two values.
- Automatic matching, driver actions and Pricing's finalFare remain unchanged. No prepayment, locked fare or new trip lifecycle statuses.
- For PAYOS trips, TripCompleted must not auto-charge the simulator or publish PaymentSucceeded. Payment Service creates/reuses a pending payment from trusted completed-trip data. The passenger explicitly opens checkout; the driver sees pending/success.
- POST `/api/payments/{tripId}/checkout` creates/reuses the payOS hosted link. GET `/api/payments/{tripId}/checkout` returns backend payment state. Passenger owns the trip; assigned driver may read state but never create checkout. Verify identity using the original signed bearer, not untrusted caller IDs. No frontend amount/passengerId/callback URL inputs.
- Payment Service reads canonical Trip data via the existing internal-key protected GET `/api/trips/{id}`. Require COMPLETED and PAYOS before starting checkout; use finalFare (positive integer VND), passengerId and currency from Trip. Already paid returns success without another link.
- Server-controlled return/cancel URLs point back to rider.html with trip reference. Browser return parameters never mark a payment successful.
- POST `/api/payments/webhooks/payos` is public at Gateway but verified with the payOS SDK checksum. Validate orderCode, paymentLinkId, successful status, currency and amount against stored attempt. ACK only after durable handling; repeated valid delivery does not double ledger or outbox. Ignore provider test notifications safely without creating payments.
- Persist numeric orderCode before the provider call, generated by database sequence (never truncated UUID/time-only). A failed/timed-out create is uncertain: resolve existing order before any retry. Reuse a valid pending link, reconcile expired/cancelled links before allowing another attempt; never create a second active link concurrently. Record unexpected/duplicate/partial/late money for review instead of silently crediting twice.
- On verified full payment, atomically set SUCCESS, record CAPTURE ledger and PaymentSucceeded outbox. Trip's existing COMPLETED -> PAID and Notification consumers remain.
- A bounded reconciliation scheduler queries pending/uncertain payments via payOS to recover missed webhooks; browser polls only backend. Transient provider errors or checkout cancellation never emit terminal PaymentFailed for the trip.
- Existing mock charge/refund behavior remains for MOCK. The simulated refund endpoint must not claim to refund a PAYOS payment. Real refunds and driver payouts are excluded.

## Configuration
Use official payOS Java SDK, verified against current docs/source. Secrets only in Payment Service: PAYOS_CLIENT_ID, PAYOS_API_KEY, PAYOS_CHECKSUM_KEY. Also require explicit server return/cancel base URL and public webhook registration. No secrets are currently configured: show clear unavailable checkout until configured, never fall back to a fake success. Keep live payment and webhook registration disabled without credentials.

## Architecture and contracts
TripResponse adds `paymentProvider` (string MOCK/PAYOS), `currency` (VND); CreateTripRequest adds validated provider; Trip entity stores provider; TripCompleted payload adds provider with no change to existing monetary/event fields.
Payment Service owns all payOS SDK calls, state, reconciliation and webhook verification. Gateway routes exact checkout/webhook paths and grants webhook exception only on exact POST path. Existing charge/refund stay internal.
Checkout response fields: `tripId`, `paymentId` (nullable before pending row), `status` (PENDING/SUCCESS/EXPIRED/CANCELLED/REVIEW_REQUIRED/UNAVAILABLE etc), `amount`, `currency`, `checkoutUrl` (only payable pending link), `expiresAt`, `provider` (`PAYOS`), optional readable message. HTTP 503 for missing config/upstream outage; distinguish 404 missing payment from service outage. Only matching owner/assigned driver can read.

## Verification
Backend tests cover postpay provider separation, canonical amount/ownership, fake/mismatched/duplicate webhook, concurrent checkout and uncertain timeout, reconciliation, no terminal failure on browser cancel, and refund refusal for PAYOS. Gateway tests cover exact routing and role access. UI tests cover completed -> pending -> paid, no checkout before complete, double-click protection and no success from return URL. Explicit SQL migrations before restarting services; preserve existing data. Live money flow requires user's payOS channel credentials/public HTTPS webhook and is not claimed tested without them.
