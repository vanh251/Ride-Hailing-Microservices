# payOS Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans; independent Trip and Payment work may run in parallel per dispatching-parallel-agents, with fixed contracts below.

**Goal:** Add payOS hosted checkout after trip completion, verified webhook, reconciliation and customer/driver payment UI.
**Architecture:** Reuse Payment Service, payment ledger, Kafka Outbox and existing trip payment result handling. Select PAYOS explicitly per booking; keep MOCK as legacy API default. No prepayment.
**Tech Stack:** Spring Boot/Java 17, PostgreSQL, official payOS SDK, native browser modules.
**Spec:** `docs/superpowers/specs/2026-11-24-payos-design.md`.

## Global constraints
No prepayment. No automatic fake success in PAYOS mode. No secret values in logs/files/UI. Preserve unrelated existing changes. Work in current checkout; no commits/pushes. Do not register live webhooks or execute real transfers without configured channel and user authorization.

## Review focus
- Callback signature/data/amount mismatch and duplicate capture.
- Frontend amount/identity spoofing and direct Payment Service auth bypass.
- Provider timeout after accepted create, concurrent double-clicks and repeated TripCompleted.
- Trip paid/cancelled while a provider response is in flight; old payment attempts receiving money late.
- Old MOCK behavior remaining compatible without auto-charging PAYOS.
