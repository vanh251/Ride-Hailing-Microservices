# Demo web implementation plan

Scope: approved three-screen local demo described in the adjacent design. Execute inline using existing Spring Boot and browser APIs; no new dependencies.

1. Write failing `GatewayDemoTest` for public demo HTML/CSS/JS and protected API regression. Write `scripts/tests/demo-client-test.mjs` for auth/error handling, action gating and concurrent booking with partial failures. Run to confirm missing behavior.
2. Add static demo resources under Gateway `src/main/resources/static/demo/`; permit GET of that prefix only in SecurityConfig. Implement request/session/concurrency helpers in `client.mjs`, then implement the three-screen UI in `index.html`, `styles.css`, `app.js`. Use textContent/escaping for untrusted values. Run Node tests and full Gateway `test bootJar`.
3. Rebuild Gateway image from the isolated worktree and run browser QA against the existing dedicated acceptance Compose stack (fresh demo accounts, same backend). Exercise happy path, concurrent requests, compensation, stop/restart Payment and responsive layout. Record observed evidence and fix regressions.
4. Fresh code review under requesting-code-review skill; fix important findings. Add usage/runbook in `docs/demo-web.md`; copy reviewed changes to the source checkout after checking baseline, preserve acceptance evidence, and report URL and limitations.

Ruling: User's instruction to implement the previously proposed approach is authorization for this bounded local feature; no additional product-design approval is requested. UI design and serving static assets at Gateway are implementation choices.
